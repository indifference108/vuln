# 代码审计发现（脱敏版）：签名密钥前端硬编码 → 认证网关签名校验失效

> 依据：ARTEX task 14（finding 1905）、task 15（findings 1926/1927，意图 1921 实测、1928 定稿）、task 16 最终报告。
> 本文件为公开索引口径，**隐去密钥值、appId、签名公式与可运行 PoC**；原文见本地报送包清单。

## Source → Sink

1. **Source**：开发者门户前端 SPA bundle 为公开可下载资源，任何匿名访客均可获得。
2. **硬编码**：签名函数中内联了应用标识与 32 位签名密钥（值已脱敏），属于典型的 CWE-798 / CWE-321。
3. **可复算**：签名输入由客户端自造的非秘密字段（时间戳、随机串、版本等）与上述密钥拼接后做摘要，密钥一旦泄露，签名即可离线伪造。
4. **Sink**：统一认证网关的 cardLoginAuth 认证入口接收该签名。合法密钥签名被接受并推进到「号码密文校验」阶段；错误密钥签名在入口即被拒。
5. **叠加链**：同域另一签名接口（安全基座）的公式本身不含任何秘密，匿名即可换取有效签名令牌（finding 1927，中危）；两者叠加可完整推进认证链。

## 八项有效性判定

| # | 判定项 | 结论 |
|---|---|---|
| 1 | 源是否真实可达 | 是，公开前端资源 |
| 2 | 秘密是否真实泄露 | 是，前端内联 32 位签名密钥 |
| 3 | 客户端能否复算签名 | 能，全部输入可控 |
| 4 | 服务端是否真的校验签名 | 是，错误密钥返回「签名校验失败」 |
| 5 | 伪造签名是否被接受 | 是，返回「签名校验通过、进入下一阶段」类业务码 |
| 6 | 是否存在更前置的拦截 | 业务类型校验在签名校验之前，已用对照排除干扰 |
| 7 | 是否触达真实用户数据 | 否，仅构造测试号，止于「流程可推进」 |
| 8 | 是否可武器化 | 可构造官方域名授权页形成钓鱼面；本归档不提供实现 |

## 影响

签名机制作为统一认证网关的第一道防线失效；后续阶段仅依赖号码密文与号码绑定关系。任何取得公开前端资源的匿名攻击者可伪造有效认证请求，对任意号段构造以受害者号码为主体的官方域名授权页。

## 修复建议

1. 立即吊销/轮换泄露的应用密钥，把签名所需秘密整体迁移到服务端，前端不得出现任何签名密钥。
2. 全量排查同域及其他前端 bundle 的同类硬编码密钥，建立前端密钥扫描门禁。
3. 认证入口增加请求侧强绑定：号码密文与请求上下文绑定、一次性挑战值、timestamp/traceId 防重放、appId 与号段绑定。
4. 无密钥签名接口改为服务端下发挑战值或 HMAC 密钥（经安全信道分发至 SDK 本地组件，而非 JS）。
